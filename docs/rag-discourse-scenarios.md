# Сценарии развития RAG-индекса (discourse / кеш / чанкинг)

Документ фиксирует разбор внешних рекомендаций (discourse tree, npm-библиотеки, ускорение embed) относительно текущего TG Insight и возможные пути развития с прогнозом сложности.

Режим. Explanation (почему и что выбирать), не how-to и не спецификация API.

Дата снимка. 2026-09-12. Ветка `feature/rag-period`.

---

## Где мы сейчас (факт по коду)

- Чанкинг. `messagesToChunkDrafts` → одно сообщение → окна 1800/200. Фильтр ≥10 букв после вырезания URL.
- Reply-graph уже есть. `buildReplyChain` + `replyToId` для UI-фильтров и карточек Ask. В индекс цепочки **не** попадают (в `chunkReplyChain` уходит `[message]`).
- Embed. Локальный Transformers.js / Model2Vec в worker. Батчи 16 (WASM) / 64 (WebGPU). Батчи сериализованы на одном устройстве.
- Persist. Dexie `chunks` хранит векторы между перезагрузками. `replaceChunkIndex` при пересборке делает полный `clear` + re-embed.
- Масштаб (из `docs/rag-embed-bench.md`, export ~177k сообщений). ~165k eligible чанков на полный чат. Узкое место — **N эмбеддингов**, не алгоритм окна.

## Разбор трёх блоков рекомендаций

### 1. Discourse tree / conversation graph

Идея верная как модель домена для **качества retrieval**. Чат — не AST компилятора. Узлы-сообщения и рёбра reply / тема / intent ближе к discourse parsing, чем к токенным окнам.

Что переоценено.

- «Меньше эмбеддингов за счёт крупных структурных чанков» на первой сборке даёт выигрыш только если среднее число сообщений на чанк заметно >1 и текст не раздувается выше лимита модели. Guess. На плоском чате без reply доля выигрыша часто скромная.
- «Инкремент как у AST» **не требует** полного topic segmentation. Достаточно стабильного id узла чанка и hash содержимого. Полный discourse-парсер — дорогой способ получить инкремент.
- Ошибки сегментации тем размазываются по индексу. Это главный риск, не сложность кода сама по себе.

Что недооценено у нас.

- Уже есть дешёвый structural signal. `reply_to`. Можно поднять качество чанков **без** LLM и без RST, если индексировать завершённые reply-ветки (или leaf+ancestors) вместо одиночных сообщений.

### 2. Библиотеки JS/TS

Семантический чанкинг текста (Chonkie, semantic-chunker, LangChain splitters) решает другую задачу. Документ / статья, не Telegram reply-graph. Подключение даст второй пайплайн эмбеддингов для сегментации и почти не уберёт наши 165k локальных векторов.

Threading / topic npm. Готовых прод-пакетов по сути нет. `conversation-tree` на LLM-классификации — прототип, не drop-in для client-side privacy RAG.

Вывод. Библиотеки не закрывают discourse для чата. Свой тонкий слой на `replyToId` (+ опционально эвристики времени/автора) рациональнее чужого text-chunker.

### 3. «Медленно из-за embedding API»

Совет про network I/O, parallel HTTP и SDK **частично мимо нашего стека**.

| Утверждение | У нас |
|---|---|
| Последовательные одиночные embed | Уже батчи в worker. Параллель батчей на одном GPU/WASM почти бесполезна. |
| Нет кеша между перезапусками | Индекс в Dexie живёт. Нет **инкрементальной** пересборки. |
| Нет дедупа одинакового текста | Верно. После фильтра коротких сообщений выигрыш часто небольшой (нужен замер на экспорте). |
| I/O-bound API | У нас compute-bound локальный inference (+ разовое скачивание модели). |

Правильный приоритет ускорения build. Сначала сократить **сколько** раз считаем embed (инкремент, scope, меньшая модель). Потом железо/батч. Discourse и npm-chunker — про качество и структуру, не про «на порядок быстрее первый прогон».

## Шкала сложности

Оценка относительно текущего репо (один разработчик, familiar с `RagContext` / Dexie / workers).

| Уровень | Смысл | Порядок трудозатрат |
|---|---|---|---|
| S | Локальный diff, тесты unit | 0.5–1 день |
| M | Несколько модулей, миграция схемы, ручной UI-прогон | 2–4 дня |
| L | Новый подсистемный контур, оценка качества retrieval | 1–2 недели |
| XL | Исследовательский парсер + прод-hardening | 3+ недели, неопределённость качества |

## Сценарии развития

Сценарии можно комбинировать. Порядок ниже — рекомендуемая очередь по отношению выигрыш / риск / сложность.

### S0. Статус-кво

Оставить message-window чанкинг, полный rebuild, батчи как есть.

- Для пользователя. Первая индексация большого чата долгая. Повторная «Пересобрать» снова долгая. Ask уже показывает карточки сообщений.
- Для мейнтейнера. Простой код. Долг на инкременте растёт с размером корпуса.
- Сложность. —
- Риск. Низкий.
- Когда ок. Малые чаты, редкая пересборка, устраивает текущий UX.

### S1. Инкрементальный индекс (id + content hash + modelKey)

Не переэмбеддить чанки, у которых ключ совпал с Dexie. Удалять отсутствующие. Добавлять только новые/изменённые.

- Данные. `ChunkRow` + `contentHash` (или hash от текста чанка). Meta `embedModel` уже есть.
- Для пользователя. Повторная сборка и догрузка периода становятся секундами или минутами вместо полного прогона. Guess до замера.
- Для мейнтейнера. `replaceChunkIndex` перестаёт быть единственной стратегией. Нужен merge-path и инвалидация при смене модели / формата чанка.
- Сложность. **M**
- Риск. Средний (баги устаревших векторов при смене chunker). Лечится version ключом формата в meta.
- Зависимости. Нет.
- Связь с discourse. Не нужна. Это прямой аналог «переиндексировать изменённый узел» на уровне чанка.

### S2. Дедуп по сырому тексту сообщения

Один embed на уникальный `message.text` (или нормализованный), несколько `messageIds`.

- Для пользователя. Небольшой выигрыш времени build, если дублей мало. На шаблонных каналах — заметнее.
- Для мейнтейнера. Усложнение retrieval/UI (один вектор → много источников). Конфликт с форматом `[#id] author` в тексте чанка.
- Сложность. **S–M**
- Риск. Средний для качества (разный контекст одной фразы).
- Рекомендация. Сначала lever. Замерить `unique(text)/count` на eligible корпусе. Внедрять только если ratio заметно &lt; ~0.85. Guess порога.
- Связь с advice. Подтверждает пункт про дедуп, но не как главный рычаг.

### S3. Structural chunking по reply-chain

Индексировать не одиночное сообщение, а `buildReplyChain(leaf)` (или только leaves / корни веток) как один смысловой чанк. Длинные ветки резать окнами как сейчас.

- Для пользователя. Лучше самодостаточные куски «вопрос–ответ». Меньше разорванного контекста в Ask.
- Для мейнтейнера. Меняется cardinality чанков и `messageIds`. Нужна стратегия «какой id matched» при retrieval (уже есть `matchedId` в UI).
- Сложность. **M**
- Риск. Средний. Плоские сообщения без reply остаются как сейчас. Ветки-монстры раздувают чанк.
- Зависимости. Код уже есть (`reply-chain.ts`). Почти бесплатный discourse-lite.
- Эффект на скорость build. Слабый или умеренный. Число чанков может упасть, если много reply. На плоском чате почти без изменений. Guess.

### S4. Topic segmentation / «продолжение vs новая тема»

Эвристики (разрыв по времени, смена автора, отсутствие reply) или LLM-классификатор на каждое сообщение.

- Для пользователя. Потенциально лучше границы тем в длинных flat-обсуждениях.
- Для мейнтейнера. Новый контур качества. Нужны фикстуры и метрики retrieval. LLM-путь бьёт по privacy и offline-обещанию продукта, либо тянет ключ OpenRouter на этап индекса.
- Сложность. Эвристики **L**. LLM-классификатор **L–XL** (стоимость, латентность, нестабильность).
- Риск. Высокий. Ошибки границ портят весь индекс.
- npm. Готового пакета нет. `conversation-tree` — референс идеи, не зависимость.
- Рекомендация. Не начинать отсюда. Только после S1 и замера, что S3 недостаточно на реальных чатах.

### S5. Подключить Chonkie / semantic-chunker

Семантическая группировка предложений через доп. эмбеддинги.

- Для пользователя. Сомнительный выигрыш именно на Telegram-сообщениях (короткие реплики, уже отдельные единицы).
- Для мейнтейнера. Вторая модель или BYOE-цикл. Размер бандла. Дублирование с нашим embed worker.
- Сложность. **M–L**
- Риск. Средний/высокий относительно ценности.
- Рекомендация. **Не брать** как путь ускорения. Возможный эксперимент только если нужен чанкинг длинных paste-монологов внутри одного сообщения.

### S6. Полный discourse / RST-подобный граф

Узлы, рёбра reply + citation + topic + intent. Инкремент по затронутой ветке темы.

- Для пользователя. Максимум «осмысленных» чанков в идеале.
- Для мейнтейнера. По сути исследовательский продукт внутри продукта.
- Сложность. **XL**
- Риск. Очень высокий. Нет формальной грамматики. Качество парсера = качество индекса.
- Рекомендация. Отложить. Имеет смысл как отдельная R&D ветка, не как ответ на «медленно строит эмбеддинги».

## Рекомендуемая траектория

1. **S1** (инкремент) — главный ответ на боль пересборки и прямая аналогия с «узлом AST» без discourse-парсера.
2. Lever на корпусе. Доля unique text, доля сообщений с `replyToId`, распределение длин веток. Без цифр не решать S2/S3 вслепую.
3. **S3** (reply-chain чанки) — лучший дешёвый шаг к «структурным» чанкам на уже имеющемся графе.
4. **S2** только при измеренном дубле.
5. **S4–S6** — только если retrieval-качество упирается в flat chat без reply и это подтверждено примерами Ask.

Что не выбирать как ответ на скорость первой индексации.

- Discourse tree ради «меньше векторов».
- npm semantic chunker.
- Parallel HTTP embedding advice (у нас не тот bottleneck).

## Открытые решения (продукт)

- Нужна ли пересборка «с нуля» как явная кнопка рядом с инкрементом.
- Индексировать все leaves reply-графа или только unmatched roots + orphans.
- Допустим ли LLM на этапе индекса (сейчас embed локальный, Ask опционально с ключом).

Эти развилки не закрываются экспериментом в коде без предпочтения по privacy и UX. Остальное закрывается замерами на `data/result.json` и пользовательских экспортах.
