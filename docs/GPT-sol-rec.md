Нашёл практичный вариант. Основной выигрыш даст не ML-фильтр мусора, а комбинация из четырёх изменений.

### **Что сейчас тормозит**

Текущий фильтр слабый по сокращению корпуса:

- indexable: 171 019 сообщений;
- после правила «не менее 10 букв»: 165 079;
- удаляется лишь около **3,5%**;
- одно сообщение почти всегда становится одним embedding-чанком.

Для 12 месяцев получается около 7 761 чанка. По нашему Node-бенчу:

- E5 small, 9,9 текста/с: примерно **13 минут**;
- Potion multilingual, 119 текстов/с: примерно **65 секунд**.

Браузерные цифры будут другими, но измеренная разница моделей около 12 раз.

### **Лучшее решение**

#### **1. Объединять сообщения до embedding**

Не брать 48 часов единым документом. Формировать небольшие разговорные блоки:

- объединять последовательные сообщения одного автора за 2–5 минут;
- сохранять reply-ветку или вопрос с ближайшими ответами;
- завершать блок при паузе, смене ветки или достижении 1200–1800 символов;
- сохранять все `messageIds` внутри блока.

Это дешёвая версия discourse chunking. Исследования сегментации чатов подтверждают полезность времени, автора и упоминаний как структурных сигналов: **[Information Bottleneck Inspired Method for Chat Text Segmentation](https://aclanthology.org/I17-1020/)**.

Прогноз: сокращение числа чанков может быть заметным, но коэффициент нужно измерить на реальном экспорте.

#### **2. Сделать двухуровневый индекс**

- Все сообщения попадают в быстрый BM25-индекс.
- Dense embeddings строятся только для объединённых содержательных блоков.
- Результаты BM25 и dense объединяются через RRF.
- Короткое сообщение не теряется полностью. Оно остаётся доступным по словам, именам и идентификаторам.

Для браузера подходят:

- **[MiniSearch](https://github.com/lucaong/minisearch)**, зрелый и простой;
- **[Orama](https://github.com/oramasearch/orama)**, умеет BM25, vector и hybrid;
- **[advancedRagDemo](https://github.com/vishalmysore/advancedRagDemo)**, пример локального IndexedDB + BM25 + vectors.

Это лучше агрессивного удаления мусора. Recall сохраняется через BM25, а дорогой dense-корпус уменьшается.

#### **3. Добавить инкрементальный кеш**

Ключ вектора:

modelKey + chunkerVersion + hash(normalizedChunkText)

При расширении периода с трёх до шести месяцев нужно эмбеддить только новые или изменённые блоки. Это главный выигрыш повторной сборки.

Сейчас Dexie сохраняет готовый индекс после перезагрузки страницы, но кнопка пересборки очищает его и считает всё заново.

#### **4. Фильтровать только очевидный мусор**

Безопасно удалять:

- пустые и service-сообщения;
- emoji-only, punctuation-only и URL-only;
- команды ботов без полезного текста;
- точные дубли после нормализации пробелов и регистра;
- повторяющийся шаблонный spam после измерения частоты.

Не стоит автоматически удалять:

- короткие вопросы;
- ответы внутри reply-ветки;
- сообщения с именами, датами, суммами и кодами;
- форварды целиком. Сейчас они все исключаются, хотя часть может содержать полезные знания.

Near-dedup через MinHash можно добавить позже. Есть браузерный **[nearline](https://github.com/mattgrill/nearline)**, но сначала нужно измерить долю точных дублей. MinHash не окупится, если дубли составляют несколько процентов.

### **Что не ускорит построение**

- `semantic-chunker` выполняет embeddings для поиска границ. Он улучшает структуру, но не устраняет дорогой первый проход.
- Late Chunking требует длинноконтекстной модели и решает качество контекста, а не скорость: **[jina-ai/late-chunking](https://github.com/jina-ai/late-chunking)**.
- HNSW ускоряет поиск по готовым векторам, но не их создание.
- Сервер на 2 CPU / 4 ГБ вряд ли обгонит клиентский WebGPU.

### **Рекомендуемый порядок**

1. Добавить измеритель: exact duplicates, доля reply, серии одного автора, прогноз числа новых чанков.
2. Реализовать объединение author bursts + reply-aware chunks.
3. Добавить hash-cache и инкрементальную пересборку.
4. Переключить быстрый режим на Potion multilingual.
5. Добавить BM25 + RRF, чтобы компенсировать более слабую семантику Potion и сохранить короткие сообщения.
6. Проверить 20–30 реальных запросов по Recall@5 и времени сборки.

Оценка: измеритель 0,5 дня; новый чанкинг 1–2 дня; кеш 2–4 дня; BM25/RRF 2–4 дня. Самый выгодный первый шаг сейчас — измеритель, затем author/reply chunking.

Нашлось ещё два подтверждённых узких места:

1. `ChatContext.onParsed` вызывает `clearChatData()` при каждой загрузке экспорта. Поэтому повторный импорт того же чата уничтожает пригодный индекс. Инкрементальный кеш сначала требует перестать очищать данные без проверки `chatId` и версии корпуса.
2. Worker вызывает `.tolist()` и передаёт `number[][]` через `postMessage`. Векторы копируются и затем целиком хранятся в RAM до завершения. Лучше передавать плоский transferable `Float32Array` и записывать батчи в Dexie сразу.

Эксперимент Potion WASM vs WebGPU (WSL Node, 2026-09-17): **GPU медленнее** — 84 vs 115 texts/s (`webgpu/cpu = 0.73`). Браузерный WASM ≈ Node `cpu`. На WSL WebGPU похож на software/Mesa, не на дискретную GPU. Детали: `docs/rag-embed-bench.md`, `scratch/embed-bench/device-results.json`.

Обновлённый приоритет:

1. Не уничтожать индекс при повторном импорте того же чата.
2. Content-hash delta cache.
3. Potion WASM против Potion WebGPU.
4. `Float32Array` + streaming writes.
5. BM25 + RRF.
6. Reply/author chunking.

Это важнее semantic chunking и HNSW для скорости построения.
